# Agent Track 진척 정체 원인과 개선 조치

작성 기준: 2026년 11월 14일 KST의 실제 코드·CI·운영 조회 결과. 사용자가 요청한 진척 정체 원인 기록이며, 새 개발 완료 선언이 아니다.

## 판단

진척이 제자리처럼 보인 데에는 **집계 방식의 한계와 실제 통합 작업의 지연이 함께 작용했다.** 구현과 운영 기반의 변경은 있었으나, 사용자가 원한 전체 업무의 새로운 성공 증거는 아직 없다. 같은 71.4%를 반복한 보고는 그 차이를 충분히 설명하지 못했다.

현재 71.4%는 상위 요구 21개 가운데 기존 수용 판정이 완료인 15개를 센 값이다. 모든 상위 요구를 같은 1점으로 계산하고 부분 충족 6개에는 0점을 준다. 이는 개발 작업량·운영 준비도·남은 시간의 추정치가 아니다. 기존 완료 15개도 각 기록의 소유자·QA 범위에서 누적한 판정이며, 이번에 최신 운영 환경의 모든 기능을 다시 검사한 결과는 아니다.

마지막 상위 집계 증가인 11월 13일 18:10의 14→15는 AT-18 판정 정정이었다. 11월 14일 01:51 점검까지 약 7시간 40분 동안 새 상위 수용 항목의 완료는 없었다. 따라서 수치의 정체를 표시 문제로만 설명할 수 없다.

## 원인 1. 서로 크기가 다른 요구를 한 점으로 계산했다

SNB 조절 같은 화면 요구와 Assistant→Demian→Projects·Note→desktop→Track의 전체 업무 검증이 각각 1점이다. 큰 통합 요구 AT-14 안에서 여러 단계가 끝나도 전체 사용자 경로가 닫히기 전까지 숫자는 변하지 않는다. 반대로 이 비율을 제품 전체 개발 완료율로 읽으면 남은 작업을 과소평가하게 된다.

기존 21개 분모와 요구 범위는 유지한다. 완료한 준비 작업에 사후 점수를 주거나 부분 충족을 임의로 50%·90%로 바꾸지 않는다. 상위 수용률에 구현·격리 검증·운영 반영·사용자 수용 단계를 함께 표시해야 한다.

## 원인 2. 코드 구현과 실제 운영 연결 사이에 간격이 남았다

보호된 Demian Run의 metadata를 읽는 원본 API, Assistant reader와 Track 수집기 코드는 구현·검사됐지만, 세 구성 요소가 같은 실제 업무를 운영에서 끝까지 처리한 것은 아니다. 코드 검사와 합성 upstream을 사용하는 HTTP/SQLite 검사는 실제 운영 WorkCoordinator 업무의 증거를 대신하지 못한다.

현재 새 native API와 공개 gate는 운영 중이다. 이번 후속에서 Assistant도 새 0691e1a 이미지로 운영 전환했다. 현재 역할로 native 서명 조회 세 경로의 200 응답을 확인했고, Track에 구성된 기존 전용 reader credential로 Assistant v2 capability와 업무 목록도 200으로 읽었다.

그러나 운영 Track은 여전히 a3bb446 release이고 새 보호 수집 source는 활성화되지 않았다. 새 Track release는 9639375 기준으로 별도 동결했지만 아직 운영 전환 전이다. 허용된 실제 보호 Run의 본문→Track 원장·Trace 대조도 남아 있다.

## 원인 3. 전환·보존 검증 도구를 고치는 데 시간이 길게 들어갔다

기존 업무 DB, 인증, 보고서·파일과 다른 서비스를 보존해야 하므로 전환 검사는 필요했다. 다만 전환 도구의 경로·응답 형식·Docker 표현·시작 시 데이터 변경에 대한 가정이 실제 환경과 달라 추가 수정이 발생했다.

- Windows 프로세스 경로 표기와 native RFC problem 응답 형식 가정이 달라 전환 전에 검사가 중단된 사례가 있었다.
- 새 후보 preview에서 기존 Task 문맥 재검사가 다시 일어나지 않을 것으로 잘못 가정했다. 실제로는 기존 시작 동작이 Task 3개의 revision과 UI 이벤트 6개를 변경했다. 같은 복원본에서 이 제한된 변경을 역산한 세 테이블 hash가 백업 당시와 모두 일치함을 확인했다.
- preview 앱에는 helper operation label이 없는데 정리 코드가 그 label을 요구해 정리가 실패했다. 정확한 이미지·설정·이름·네트워크·mount로 소유권을 확인한 중지 앱만 제거하고, 성공한 Docker 전체 목록 조회로 부재를 확인했다. 기존 실패 기록은 남겼다.
- Windows 소유권 시험의 종료 PID 전제를 안정시키기 위해 fixture의 native handle을 보존하고 정리를 보완했다. 생산 guard는 유지했다. 이전 CI 실패가 실제 PID 재사용 때문이었는지는 확정하지 않는다.

후속에서는 완료한 대용량 백업이나 후보 앱 기동부터 반복하지 않고 같은 복원본을 재사용했다. 현재 운영 DB의 schema·업무 행, 보고서, 선택 파일 68개와 다른 12개 서비스·renderer를 대조했다. 기존 Assistant 이미지는 중지한 채 보존했다. 실제 전원 재기동·crash 복구 시험까지 수행한 것은 아니다.

## 원인 4. 사용자 업무를 닫는 일보다 기반 보완에 작업이 오래 머물렀다

이번 지연에는 실행 우선순위와 진척 보고의 문제도 있다. 준비·전환·검증 도구의 하위 성공은 쌓였지만, 사용자가 확인할 수 있는 전체 업무 한 건을 마감하는 경로가 늦게 닫히고 있다. 같은 상위 수치를 반복하면서 그 사이 무엇이 실제 운영에 반영됐고 무엇이 실패했는지 충분히 구분하지 못했다.

desktop도 처음에는 별도 앱·bridge 계약이 필요하다고 보류했으나, 과거 사용자 지정과 현재 hostname/IP를 대조해 대상이 현재 Windows pydemia-desktop PC임을 확인했다. 이 미확정 계약을 계속 대기 조건으로 유지해서는 안 된다. 필요한 것은 이 PC에서 같은 실제 업무를 여는 검증이다.

수정 커밋 9639375의 [CI 43468025771](https://github.com/pydemia/agent-track/actions/runs/43468025771)은 Windows·Ubuntu 모두 통과했다. 이 결과를 전체 사용자 업무의 완료로 확대하지 않는다.

## 이후 작업과 보고 방식

1. 새 Track release와 보호 수집 source를 운영 연결한다.
2. 실제 업무 한 건에서 원본 Task·Run·receipt·결과·Note 참조를 같은 식별자로 대조한다. Track의 Trail·Trace·Map과 그룹에서 의미 있는 흐름·근거를 확인한다.
3. 남은 6개 요구의 사용자 조건을 각각 닫는다. 기존 요구 범위를 줄이거나 별도 desktop 앱·추가 screenshot export 같은 조건을 새로 붙이지 않는다.
4. 보고마다 수용 판정, 이번에 닫힌 사용자 조건, 실제 운영 반영, 현재 실패·미지원과 다음 수용 검사를 구분한다. 새 변경·실패 없이 같은 검사를 반복한 것은 진척으로 세지 않는다.

**전체 수용 판정은 15/21·71.4%(상위 동일 가중치·부분 0)로 유지한다. 전체 개발 완료율은 별도로 산정하지 않는다.** 전체 완료 예상은 아직 산정하기 어렵고 신뢰도는 낮다. 첫 전체 업무의 결과와 원본 재개·재시도 구현 범위를 확인한 뒤 재산정한다. 전체 goal은 원래 범위로 계속 진행한다.

이 문서의 Note 게시 자체는 요청받은 원인 기록이다. WorkCoordinator 전체 업무 성공이나 AT-14 완료 증거로 계산하지 않는다.
