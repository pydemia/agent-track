# 계정별 Flow 저장 보기

2026-11-13 · AT-12-G06 · 구현·격리 검증. 운영 게시 전.

그룹 컨트롤의 `계정별 저장 보기`에서 현재 묶음 이름과 구성, 묶음 기준,
탐색 깊이, 그룹별 접힘과 내부 초점을 저장한다. 다음 접속에서 같은 흐름을
열고 저장 보기를 선택해 `선택 보기 불러오기`로 복원한다. 마지막 선택을
자동 적용하거나 현재 화면의 네 보기 공통 범위를 영속 저장하는 기능은 아니다.
원본 업무·의존성·담당자·Run·실행 명령은 변경하지 않는다.

저장 이름은 사용자가 작성한다. 원본 Task/Run 이름·대화·도구 인자는 복사하지
않는다. 구성은 source-qualified Task·Run·Assistant execution ID를 기준으로
검사한다. 표현 상태의 node/group key는 권한을 부여하지 않는다. 복원 시 현재
그래프에 없는 구성원이 있으면 적용하지 않으며, 사라진 그룹의 접힘/초점 key는
제거한다. 새로 관측한 실행이 추가돼도 기존 묶음의 권한 재검사를 유지한다.

## 화면 동작과 보존 범위

| 동작 | 결과 |
| --- | --- |
| 새 보기 저장 | 현재 계정·흐름에 새 UUID로 생성. 현재 원본 접근 재확인 |
| 선택 보기 불러오기 | 새 서버 조회와 현재 그래프 대조 후 묶음·접힘·깊이·내부 초점 복원 |
| 현재 구성으로 덮어쓰기 | 선택 당시 revision과 비교. 다른 화면의 변경을 조용히 덮어쓰지 않음 |
| 선택 보기 삭제 | 계정 소유와 revision 확인 후 삭제. 그 보기에서 복원한 표현은 초기화 |
| 목록 다시 확인 | 현재 원본 접근으로 목록 갱신. 철회된 이름·선택·복원 그룹 제거 |

계정/흐름 전환, 늦게 도착한 응답, 이전 조회 실패는 다른 계정이나 새 수동
작업 결과에 적용하지 않는다. 새 관측으로 요청 세대가 바뀌어도 복원한 보기의
권한 추적은 계정·흐름에 유지한다. 조회 실패 때 이전 이름을 성공 결과로
유지하지 않는다. 저장 응답 후 새 GET에서도 같은 ID/revision을 확인해야
저장 이름과 선택을 게시한다.

목록·저장은 원본 Task metadata, Demian Run/Session, Assistant execution과
현재 Projects 교집합을 확인한다. 로컬 Codex는 현재 허용된 수집 원장의
source/Run을 확인한다. 권한이 사라진 보기는 이름을 반환하지 않으며, 원본
단절은 빈 정상 목록과 구별한다. 계정별 저장은 기존 Entra/내부 proxy 신뢰
경계를 사용하며 별도 사용자 이름·비밀번호 로그인을 추가하지 않는다.

## 저장·API와 제한

SQLite `saved_flow_views`는 `(actor,id)` 기본키를 쓰는 추가 테이블이다.
`Store`의 기존 schema version2를 바꾸지 않으며 이전 프로그램도 기존 원장을
읽을 수 있다. 기존 원장·cursor·receipt 테이블은 수정하지 않는다. 생성/갱신과
삭제는 트랜잭션의 revision 비교로 처리한다. 계정당20개, 보기당 명시 기준
항목32개, 내용12KiB가 상한이다. 기준 항목은 Task/Run/Assistant execution이며
호출·도구 node 수나 그룹 깊이와 같은 단위가 아니다. 현재 전체 그래프가
32기준 항목을 넘으면 더 작은 묶음 범위에서 저장해야 한다.

| API | 현재 동작 |
| --- | --- |
| `GET /api/flow-views?contextId=<sha256>` | 인증 계정·흐름의 현재 허용 보기만 반환 |
| `POST /api/flow-views` | strict 본문·같은 origin·현재 인증/원본 권한·revision 검사 후 생성/갱신 |
| `DELETE /api/flow-views/<uuid>` | 같은 origin·현재 인증 계정의 소유·revision 확인 |

공개 응답은 actor와 bounded 내용만 포함하며 원본 credential은 포함하지 않는다.
요청 시작부터 본문·인가·최종 저장까지 서버10초, 브라우저12초 경계를 적용한다.
권한 조회가 늦게 완료돼도 만료/철회한 요청을 저장하지 않는다. 처리 중 다른
계정으로 바뀌거나 인증 key가 바뀌면 저장 직전 다시 거부한다.

## 현재 증거와 운영 후속

실제 loopback HTTP의 native GET 인가·거부, 다른 Session 참조·source 단절,
actor/Project 철회, CAS, 느린 body/인가와 뒤늦은 완료의 무저장, 계정 분리와
SQLite 닫기/재열기를 검사했다. 합성 브라우저에서는 묶음 생성·접힘·저장·
프로세스 재시작/새로고침·선택 복원·이름 갱신,390px 컨트롤 범위와 Tab/Enter를
확인했다. 원본 Task 읽기만 철회하고 현재 그래프를 유지하는 조건에서 기존
입력/복원 그룹 이름이 남는 증상을 재현한 뒤 제거를 확인했다. 이어 새 관측
Run을 추가해2node/1edge→4node/3edge로 바꾼 뒤 같은 철회를 검사했다.

이 브라우저 fixture는 원본 업무 실행이나 실제 추가 기기의 증거가 아니다.
스크린샷·최종 운영 Entra GUI와 실제 owner 저장/복원은 미검증이다. 운영
테이블 생성·API 재시작과 프런트엔드 게시 전에 Track DB/설정 backup과 현재
프로세스·미종료 receipt를 확인하고, 개발 build와 운영 정적 경로를 분리해야 한다.
검증 중 기본 Vite build가 운영 `dist/web`를 갱신한 것을 발견해 원래 동결
프런트엔드를 복원했다. 실제 HTTP18파일 byte/hash와 Track/Demian 프로세스
보존을 확인했다. 이후 후보는 private staging으로 빌드했다.
로컬 확인 명령은 `npm run build:check`이며 저장 기능은 아직 운영에 게시하지 않았다.

기획·UI 검증은 AT-12의 부분 범위다. 전체14/21개(동일 가중치66.7%)·ETA 산정
불가·신뢰도 낮음을 유지한다. Entra/교차 앱/추가 기기와 실제 조직화 수행이
남아 있다. 최종 검사·산출물 hash와 CI는 `saved-flow-views-verification.json`에
기록한다.
